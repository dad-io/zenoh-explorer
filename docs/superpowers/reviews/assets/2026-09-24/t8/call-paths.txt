  Buffer thread timing (zenoh_worker.rs:15-68):
    MessageReceived: batched; flushed after 1 ms with no new event (recv_timeout 1 ms, :23/:45-47), at 50 messages (:29),

  After 15 s without a Pong, worker_healthy = false -> header "Worker Unresponsive" pulsing red (app.rs:345-363).
  The 15 s clock runs from the LAST Pong (events.rs:145, :161). Pongs normally return about every 5 s, so a long arm shows the
  label about 10-15 s after it starts (15 - time since the last Pong). [corrected after review]

  (F-T13-13). Their shared state carries scroll_stuck_to_end = false from the history view, and egui only re-sticks when the
  offset reaches the end (scroll_area.rs:979, :1242). "Auto-scroll" is ticked in the capture but has nothing to hold on to.
  Precise condition (scroll_area.rs:1242-1245): the history leaves stuck=false only when its offset is NOT at its end. light-1400-04
  shows temp1's history at offset 0 (13:55:18.379 newest on top, list overflows). Offset 0 came from the previous place, report,
  whose empty history clamped the shared offset to 0 (scroll_area.rs:1117-1118, :1234).
  Conclusion: scroll position, not processing lag. Covered by F-T13-13 (T8 proposes a correction to it). Live confirmation pending (coordinator).

PUBLISH DEDUP RACE [added after review]
  With a user subscription covering the key, the local subscriber task (zenoh_worker.rs:375 -> :403-416, is_local=false) and the
  echo (:635) carry the same key+payload hash. Whichever commits first survives. If the subscriber copy wins, the echo is deduped
  and the local marker and PUT row never appear, even on a first publish. Either order is possible; neither has been observed.
